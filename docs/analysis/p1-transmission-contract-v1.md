# Phase 1 transmission contract v1

- Date: 2026-07-14
- Task: `TASK-260712-51y5k9`
- Story: `STORY-260712-25lysg`
- Contract version: `p1-transmission-v1`

This note is normative for the phase-one transmission store, HTTP API,
WebSocket codecs, scheduler, node clients, history projection and Telegram
adapter. It resolves the deliberately logical examples in
`docs/spec-self-contained-audio.md`. A later implementation may add optional
fields or new enum members only behind a negotiated capability; it must not
change a rule below while advertising the v1 capabilities.

`MUST`, `MUST NOT`, `SHOULD` and `MAY` have their usual RFC 2119 meanings.
This is engineering scope. Listening, packaged-application and physical-device
evidence belongs to manual epic `EPIC-260714-th54l3`.

## 1. Common representation and invariants

### 1.1 IDs, JSON and time

- Transmission IDs are `tr_` plus a 26-character Crockford ULID. The ULID is
  generated by the coordinator and is never accepted from a caller.
- Media IDs use the existing `m_` plus 26-character ULID identifier. Public
  orbit IDs are positive JSON integers and installation slots are lowercase
  `a` through `z`.
- HTTP request objects are strict JSON: unknown fields, duplicate fields,
  explicit `null`, trailing values and bodies over 16 KiB are rejected as
  `400 invalid_request`. Optional fields are omitted rather than set to null.
- HTTP timestamps are RFC 3339 UTC with millisecond precision. Persistence
  stores Unix milliseconds. WebSocket coordinator-clock fields end in
  `_coord_ms` and are signed 64-bit milliseconds.
- WebSocket messages use the existing v1 envelope from `docs/protocol.md`.
  Envelope `id` and `ts` are diagnostic only and never authorize or order a
  transmission.

### 1.2 Trusted acceptance and ordering

`accepted_at` is captured once by the coordinator at the first authenticated
application-service ingress that can create a transmission:

- for HTTP, after credential resolution and before body-dependent repository
  work;
- for Telegram legacy voice, when processing becomes `ready` and the default
  `after_current` intent is created; and
- for an explicit local action, when that action reaches the same service.

A rejected request or an interrupt confirmation challenge has no
`accepted_at` and reserves no FIFO position. A confirmed fallback receives a
new coordinator timestamp. An exact idempotent retry reuses the stored value.
No request or callback field can supply or override it.

The stable order key is `(accepted_at_ms ASC, transmission_id ASC)`. This order
is used by one overlay/interrupt controller per playback domain and by bot and
history presentation. Parallel media processing cannot change it.

### 1.3 Delivery, media and origin enums

The phase-one enums are:

| Field | Values |
| --- | --- |
| `requested_delivery`, `effective_delivery` | `overlay`, `interrupt`, `after_current` |
| reserved delivery values | `queue`, `replace` (phase two; rejected in phase one) |
| clip `kind` | `voice_clip`, `audio_clip`, `builtin_cue` |
| reserved kind | `audio_track` (phase two) |
| `origin_kind` | `microphone`, `file`, `telegram`, `builtin` |

Only clip kinds accept the three phase-one deliveries. `audio_track` with
`overlay`, `interrupt` or `after_current`, and a clip with `queue` or `replace`,
returns `422 delivery_kind_mismatch`. A recognized but not-yet-enabled
`queue`/`replace` request returns `422 delivery_not_supported`.

An `overlay` clip must have `duration_ms <= 60000`. A longer request is not
silently changed; it returns `422 overlay_duration_exceeded` with ordered
alternatives `interrupt`, then `after_current`. The same limit determines
whether overlay is available in an interrupt fallback challenge.

That error uses the same actionable alternative object as confirmation, but
without a token:

```json
{
  "error":{
    "code":"overlay_duration_exceeded",
    "message":"Overlay is limited to 60 seconds.",
    "details":{
      "alternatives":[
        {"delivery":"interrupt","available":true},
        {"delivery":"after_current","available":true}
      ]
    }
  }
}
```

`available` reflects the current capability result. Selecting interrupt still
uses the ordinary interrupt-confirmation flow if exact resume is unavailable.

`origin_kind` describes how the current intent was produced; it does not carry
identity. App and local callers send it explicitly, the Telegram adapter sets
`telegram`, and the built-in test service sets `builtin`. The service derives
the origin actor, orbit and slot from authenticated `ActorContext`; identity
fields in the JSON are forbidden. Since `include_origin` is an explicit user
choice anyway, `origin_kind` is a behavior input rather than an authority
grant. It is persisted for audit and history.

`include_origin` is an optional Boolean with these defaults:

| `origin_kind` | Default | Reason |
| --- | --- | --- |
| `microphone` | `false` | avoid delayed local microphone playback |
| `file` | `true` | file send is expected to include the local Pulsar |
| `telegram` | `true` | Telegram has no authenticated originating installation |
| `builtin` | `true` | local self-test must include its initiating Pulsar |

An explicit Boolean overrides the default. Filtering applies only when the
authenticated context has an installation slot. `this_pulsar` requires that
slot and always resolves to it; `include_origin=false` with `this_pulsar` is
`400 invalid_request` rather than an empty delivery.

## 2. Audience resolution and authorization

### 2.1 Request shape

`audience` is one of:

```json
{"kind":"this_pulsar"}
```

```json
{"kind":"own_barycenter"}
```

```json
{"kind":"current_air"}
```

```json
{
  "kind":"explicit",
  "targets":[
    {"kind":"barycenter","orbit_id":41},
    {"kind":"pulsar","orbit_id":42,"slot":"b"}
  ]
}
```

`targets` is required and non-empty only for `explicit`; it is forbidden for
the other kinds. At most 64 selectors are accepted. Duplicate selectors and a
Barycenter plus one of its Pulsars are deduplicated before origin filtering.
The response exposes the resolved installation count, not the input selector
count.

Phase-one resolution is:

- `this_pulsar`: the caller's currently bound orbit and slot;
- `own_barycenter`: every current, non-revoked installation binding in the
  caller's active orbit;
- `current_air`: the caller's orbit when it is separate, or both orbits in the
  one active pairwise approach when joined; and
- `explicit`: current installations selected from the caller's own orbit or
  that one active approach only.

An explicit ID outside that domain, a stale/revoked slot and a guessed ID all
collapse to `404 audience_not_found`. The server never allows a numeric ID to
address an arbitrary tenant.

### 2.2 Immutable snapshot

Resolution and persistence happen in the create transaction. Each target row
snapshots at least `(orbit_id, slot, actor_id, binding generation)`. Online and
offline installations are both included. Later joins, replacement bindings or
new approach membership cannot expand the snapshot. A revoked/replaced target
cannot use the old row to authenticate.

Origin filtering runs after selector expansion. Zero selectors before
filtering returns `422 audience_empty`; zero after filtering also returns
`422 audience_empty`, except for the invalid `this_pulsar` combination above.

The following checks are evaluated in this stable precedence for every
snapshotted target:

1. recipient block -> terminal `blocked`;
2. effective DND -> terminal `missed_dnd`;
3. offline/stale presence -> terminal `missed_offline` for overlay/interrupt;
4. negotiated capability -> mandatory delivery decision; and
5. prepare/decode/readiness -> runtime receipt.

This ordering prevents connection state from revealing whether a recipient
blocked the sender. Sender-facing detail says only `blocked`; it never names
the blocking actor or rule.

A **mandatory target** is a snapshotted target that is online, not blocked and
not suppressed by effective DND at capability-decision time. Offline, DND and
blocked rows remain in history but do not force a capability downgrade.

### 2.3 Media authority

Create requires a live, non-satellite control capability or the equivalent
verified Telegram application-service principal. The media must be `ready`,
unexpired and owned by the caller's source orbit. Active `primary` and
`companion` actors may send any media owned by that orbit, matching the
existing owner/control media boundary. Satellite and all cross-orbit media
references fail without disclosing media state.

A target row grants media download only to the exact current actor/slot binding
that was snapshotted. A `blocked` row grants metadata receipt visibility but
never byte access. Current approach membership, copied IDs, presence, a legacy
WAV path and current orbit membership alone grant nothing.

## 3. HTTP contract

All three routes reject query parameters. They use the existing bearer
credential header and the existing error envelope:

```json
{
  "error": {
    "code": "invalid_request",
    "message": "The request is malformed or contains invalid parameters."
  }
}
```

Only errors that need actionable structured data add `error.details`.

### 3.1 Create transmission

`POST /v1/transmissions` requires exactly one `Idempotency-Key` matching
`^[A-Za-z0-9][A-Za-z0-9._:-]{15,127}$` and this body:

```json
{
  "media_id":"m_01J00000000000000000000000",
  "audience":{"kind":"current_air"},
  "delivery":"overlay",
  "origin_kind":"microphone",
  "include_origin":false
}
```

`include_origin` is optional. `fallback_confirmation` is the only other
allowed field and is valid only for confirmation of an original `interrupt`:

```json
{
  "media_id":"m_01J00000000000000000000000",
  "audience":{"kind":"current_air"},
  "delivery":"interrupt",
  "origin_kind":"microphone",
  "fallback_confirmation":{
    "token":"fc_opaque-random-value",
    "delivery":"overlay"
  }
}
```

The idempotency scope is `(actor_id, key)`. A canonical hash covers every
original field, including the resolved origin default but excluding
`fallback_confirmation`. An exact retry returns the same transmission with
`200` and `reused=true`; the first committed create returns `201` and
`reused=false`. Reuse with different original fields returns
`409 transmission_idempotency_conflict`.

Success returns:

```json
{
  "transmission_id":"tr_01J00000000000000000000000",
  "media_id":"m_01J00000000000000000000000",
  "audience":{"kind":"current_air","target_count":3},
  "origin_kind":"microphone",
  "include_origin":false,
  "requested_delivery":"overlay",
  "effective_delivery":"after_current",
  "downgrade_reason":"mandatory_target_missing_overlay_capability",
  "accepted_at":"2026-07-14T07:10:11.123Z",
  "expires_at":"2026-07-14T07:15:11.123Z",
  "status":"accepted",
  "target_counts":{
    "accepted":2,
    "preparing":0,
    "ready":0,
    "scheduled":0,
    "playing":0,
    "cancelling":0,
    "played":0,
    "missed_offline":1,
    "missed_dnd":0,
    "missed_not_ready":0,
    "blocked":0,
    "failed":0,
    "cancelled":0,
    "expired":0
  },
  "can_cancel":true,
  "reused":false
}
```

All `target_counts` keys are always present. `downgrade_reason` is omitted when
requested and effective delivery match. A top-level `reason_code` is omitted
until a terminal aggregate has one under section 4.2. `Location` is
`/v1/transmissions/{transmission_id}`.

### 3.2 Capability and downgrade behavior

Fresh capability state comes from the authenticated connection whose binding
matches the target row. Presence older than 12 seconds is offline, not an
unknown capability.

| Requested mode | Mandatory target requirement | Result when missing |
| --- | --- | --- |
| `overlay` | `media_clip_v1` and `overlay_mix_v1` | the whole transmission becomes `after_current`; one visible downgrade reason |
| `interrupt`, no main program | `media_clip_v1` and `interrupt_resume_v1` | confirmation challenge |
| `interrupt`, main active | both capabilities plus runtime `interrupt_resume_ready=true` | confirmation challenge |
| `after_current` | legacy `play_voice` compatibility or the equivalent main-session bridge | accepted on the persistent main-session path |

An overlay is never split into overlay for modern targets and after-current for
legacy targets. The stored `effective_delivery` changes once, before any
prepare is sent, and every deliverable target follows it. The exact automatic
reason is `mandatory_target_missing_overlay_capability`.

Capabilities are checked again when the FIFO head opens its barrier. If an
overlay capability was lost before any prepare, the same atomic whole-delivery
downgrade occurs and GET/history immediately shows it. After any prepare was
sent, a capability loss fails only that target as
`failed/capability_lost`; it cannot change the mode of already prepared peers.
An accepted interrupt that later loses exact capability fails the affected
target as `failed/interrupt_capability_lost`; it never invents a fallback.

### 3.3 Explicit interrupt fallback confirmation

When any mandatory target cannot provide exact interrupt semantics, no
transmission or target row is created. The API returns `409
requires_confirmation`:

```json
{
  "error":{
    "code":"requires_confirmation",
    "message":"Interrupt cannot be honored for all selected targets; choose an explicit fallback.",
    "details":{
      "confirmation_token":"fc_opaque-random-value",
      "expires_at":"2026-07-14T07:15:11.123Z",
      "alternatives":[
        {
          "delivery":"overlay",
          "available":true,
          "reason":"interrupt_resume_unavailable"
        },
        {
          "delivery":"after_current",
          "available":true,
          "reason":"interrupt_resume_unavailable"
        }
      ]
    }
  }
}
```

Alternatives are always ordered overlay, then after-current. Overlay remains
in the array with `available=false` and reason
`overlay_duration_exceeded` or `mandatory_target_missing_overlay_capability`
when it cannot be honored as overlay. A client may confirm only an available
alternative.

The token contains at least 128 bits of randomness, is stored only as a hash,
expires after five minutes, and is bound to actor, idempotency key, canonical
original request and offered delivery. The confirming POST repeats unchanged
original fields and the same idempotency key. It consumes the token and gets a
new coordinator `accepted_at`. A confirmed overlay is exactly overlay; it is
not subject to the ordinary silent overlay-to-after-current downgrade. The
stored reasons are `sender_confirmed_overlay_fallback` and
`sender_confirmed_after_current_fallback`.

Availability is rechecked transactionally. If it worsened, the API returns a
new `requires_confirmation` challenge and schedules nothing. If it improved,
the explicitly chosen fallback is still honored. Expired, replayed,
wrong-actor, wrong-key and mismatched tokens all return the same
`409 confirmation_invalid` without disclosing which check failed.

### 3.4 Status

`GET /v1/transmissions/{id}` returns the create response fields except
`reused`, plus `targets`. The creator and a current source-orbit `primary` see
all rows. Other current source-orbit actors and exact snapshotted actors see
aggregate counts plus only rows bound to their actor. Internal moderation may
use a separate audited service principal; it is not a reusable user token.
Everyone else, including a current approach member not in the snapshot, gets
`404 transmission_not_found`.

A target row is:

```json
{
  "orbit_id":42,
  "slot":"b",
  "status":"played",
  "reason_code":"completed",
  "ready_at":"2026-07-14T07:10:12.020Z",
  "scheduled_at":"2026-07-14T07:10:12.024Z",
  "started_at":"2026-07-14T07:10:12.621Z",
  "ended_at":"2026-07-14T07:10:16.812Z"
}
```

Timestamp and `reason_code` fields are omitted until applicable. Actor IDs,
credential generations, URLs, titles, filenames, local paths, tokens and raw
capability diagnostics are never returned.

### 3.5 Sender cancellation

`POST /v1/transmissions/{id}/cancel` requires a strict empty object `{}`. It is
authorized for the creating actor, a current source-orbit `primary`, or an
audited internal moderation principal. Audience membership alone cannot
cancel.

Cancellation is allowed only while no target has durably entered `playing` or
`played`. It atomically marks unsent targets `cancelled/sender_cancelled` and
sends generation-bound `cancel_media(action=disarm)` to prepared, ready or
scheduled targets. Those rows enter `cancelling` until acknowledgement. The
response is:

```json
{
  "transmission_id":"tr_01J00000000000000000000000",
  "status":"cancelling",
  "changed":true,
  "reason_code":"sender_cancelled"
}
```

`status` is the current aggregate: it is `cancelled` immediately when no node
acknowledgement is needed and otherwise `cancelling` as in the example.
Repeating a successfully requested sender cancellation returns `200` with
`changed=false` and the then-current aggregate status. If any target started
or completed, or the transmission already reached a different terminal
outcome, the endpoint returns `409 transmission_state_conflict` and mutates
nothing. This restriction is specific to sender cancel; delete, moderation,
block and DND safety actions may stop active playback as defined below.

The writer transaction also decides a cancel/start race. If `media_started`
commits first, cancel returns the conflict above. If sender cancel commits
first, cancellation wins even when the node crossed T before receiving
`disarm`: the coordinator follows with `fade_stop`, the target ends as
`cancelled/sender_cancelled`, and an interrupted main resumes exactly once.

## 4. Durable lifecycle and receipts

### 4.1 Target states

Target states are:

```text
accepted -> preparing -> ready -> scheduled -> playing -> played
                 |         |          |           |
                 +---------+----------+-----------+-> cancelling -> cancelled

terminal without playback:
missed_offline | missed_dnd | missed_not_ready | blocked |
failed | cancelled | expired
```

`played`, all three `missed_*` states, `blocked`, `failed`, `cancelled` and
`expired` are terminal. A target becomes `played` only after one valid
`media_ended(reason=completed)`. A start is not success.

The stable `reason_code` vocabulary is:

| Status | Allowed reasons |
| --- | --- |
| `played` | `completed` |
| `missed_offline` | `offline_at_acceptance`, `offline_before_prepare`, `offline_before_start` |
| `missed_dnd` | `local_dnd`, `orbit_dnd` |
| `missed_not_ready` | `prepare_deadline` |
| `blocked` | `actor_blocked`, `orbit_blocked` |
| `failed` | `media_download_failed`, `media_auth_failed`, `media_expired`, `hash_mismatch`, `decode_failed`, `duration_mismatch`, `clock_unsynchronized`, `stale_play`, `device_unavailable`, `audio_graph_failed`, `connection_lost`, `capability_lost`, `interrupt_capability_lost`, `cancel_unacknowledged`, `internal_error` |
| `cancelled` | `sender_cancelled`, `media_deleted`, `media_expired`, `moderation_disabled`, `approach_left`, `approach_apart`, `target_revoked`, `dnd_enabled`, `sender_blocked`, `coordinator_restarted` |
| `expired` | `delivery_expired` |

`cancelling` carries the intended cancellation reason. A target that was never
sent to a node may move directly to `cancelled`.

### 4.2 Aggregate states

Transmission status is one of:

```text
accepted | preparing | scheduled | playing | cancelling |
played | partial | failed | cancelled | expired
```

While any row is nonterminal, precedence is `playing`, `cancelling`,
`scheduled`, `preparing` (including `ready`), then `accepted`. Once all rows
are terminal:

1. all `played` -> `played`;
2. at least one `played` and at least one other terminal state -> `partial`;
3. no `played` and a transmission-level sender/delete/moderation cancellation
   was committed -> `cancelled`;
4. no `played` and delivery expiry was the transmission-level cause ->
   `expired`; and
5. every other no-success outcome, including all offline, all DND, all blocked
   and no-ready -> `failed`.

This rule is deterministic and is shared by HTTP, history, UI and Telegram.
The terminal top-level `reason_code` is also fixed:

| Aggregate | Reason |
| --- | --- |
| `played` | `completed` |
| `partial` | `partial_delivery` |
| `cancelled` | the committed transmission cause: `sender_cancelled`, `media_deleted`, `media_expired`, `moderation_disabled`, `approach_left`, `approach_apart` or `coordinator_restarted` |
| `expired` | `delivery_expired` |
| `failed` with no target eligible at acceptance | `no_eligible_targets` |
| `failed` after a barrier with no ready target | `no_ready_targets` |
| other `failed` | `all_targets_failed` |

### 4.3 Delivery expiry and retention

`expires_at` is the last coordinator time at which new playback may begin; it
is not history retention and does not shorten the media item's own retention.
It follows the original user intent, so a speak-now request cannot become a
days-late queue item merely because it used a fallback.

- requested `overlay` or `interrupt`, including automatic or confirmed
  after-current fallback: `min(media.expires_at, accepted_at + 5 minutes)`;
- directly requested `after_current`: `media.expires_at`, preserving the
  existing persistent main-queue policy.

At expiry, non-started rows become `expired/delivery_expired`, prepared nodes
are disarmed and an overlay/interrupt is never replayed on reconnect. A row
already `playing` may finish unless media is deleted or expires, moderation
disables it, the recipient blocks the sender or effective DND becomes stricter.
Active media expiry uses the same fade-stop table with reason `media_expired`.
History metadata follows the separate 30-day policy; byte access still ends at
media delete/expiry. A missed clip may remain visible and manually actionable
until media expiry, but manual replay creates a new transmission and acceptance
time.

### 4.4 Sender delete and moderation disable

Media delete first revokes all new downloads in its successful transaction,
then emits an idempotent lifecycle cancellation keyed by media ID and delete
generation. Moderation disable uses the same behavior and cannot be weaker.

| Target at delete commit | Required outcome |
| --- | --- |
| `accepted` or queued `after_current` | remove/disarm queue work; `cancelled/media_deleted` |
| `preparing` or `ready` | send `cancel_media(action=disarm)`; acknowledge as `cancelled/media_deleted` |
| `scheduled` | disarm if T has not started; if the start race was won, use active behavior |
| `playing` overlay | 120 ms clip fade-to-zero, then normal 600 ms duck release; `cancelled/media_deleted` |
| `playing` interrupt | 120 ms clip fade-to-zero, resume the captured main position exactly once with 120 ms fade-in; `cancelled/media_deleted` |
| `played` | keep the `played/completed` receipt; content and replay actions disappear |

Prepared/scheduled/playing rows enter `cancelling`. The node must acknowledge
within two seconds. If no acknowledgement arrives, the row becomes
`failed/cancel_unacknowledged`; download remains revoked and reconnect must not
replay the work. Whichever store transaction commits first resolves an end vs
delete race: a prior committed `played` remains played; a prior committed
delete makes a later completion acknowledgement cancelled.

Delete never blocks on the two-second acknowledgement and physical byte
cleanup remains asynchronous. The same generation-safe cancellation is used
for `approach_left`, `approach_apart`, target revocation, block and DND. A
pairwise split cancels only non-started targets on the departed side; remaining
snapshotted targets may finish and the aggregate can become partial.

## 5. Overlay/interrupt scheduler

### 5.1 Playback domain and FIFO

Exactly one controller owns overlay and interrupt for an effective playback
domain:

- a stable orbit ID while separate; or
- a stable approach ID while two phase-one orbits are joined.

Both origins in an approach share the same FIFO. Overlay and interrupt never
overlap each other. Pause, skip or replacement of the main program does not
complete or dequeue an overlay. `after_current` and confirmed after-current
fallback stay in the main Session FSM and do not serialize against an overlay
that is intentionally mixed over that FSM.

The effective domain ID is persisted at acceptance. A split does not move old
work into two controllers; it cancels departed non-started targets as above and
lets the original controller reach a terminal state.

### 5.2 Exact prepare barrier

The barrier opens only when a transmission is the FIFO head and its media is
server-ready. This avoids consuming the three-second budget while an earlier
clip is playing.

1. Persist `barrier_opened_at = coordinator now` and
   `prepare_deadline_at = min(expires_at, barrier_opened_at + 3000 ms)`.
2. Re-evaluate block, DND, online binding and capability in the defined order.
3. Send one generation-bound `prepare_media` to each remaining mandatory
   target and mark it `preparing`.
4. A target becomes `ready` only after authenticated bytes, SHA-256, exact
   expected duration and decoder/audio-graph readiness succeed.
5. Decide immediately when every mandatory target is ready or terminal;
   otherwise decide at the exact three-second deadline.
6. At decision, mark every still-preparing mandatory target
   `missed_not_ready/prepare_deadline` and never send it play.
7. If no target is ready, terminate the transmission as `failed`. There is no
   late retry or reconnect autoplay.

The barrier uses monotonic timers for waiting and persisted coordinator Unix
milliseconds for cross-process state. Timer drift never extends the persisted
deadline.

### 5.3 Exact scheduled start

Every ready target must have a valid RTT sample from its authenticated
connection no older than 12 seconds. Missing, negative or greater-than-10-second
samples make that target `failed/clock_unsynchronized` before scheduling.

Let `decision_now` be coordinator time immediately after the ready set and its
terminal misses are durably committed, and let `maxRTT` be the maximum valid
RTT of the remaining ready targets. Integer milliseconds are used:

```text
lead_ms = max(2 * maxRTT_ms + 250, 500)
T_coord_ms = decision_now_ms + lead_ms
start_deadline_coord_ms = T_coord_ms + 100
```

The coordinator durably stores T before sending `play_media_at`. A node arms
for T when its estimated coordinator time is before T. If the message arrives
between T and `start_deadline_coord_ms`, it starts immediately. If it cannot
produce the first sample by the start deadline, it emits
`media_failed(stage=schedule, code=stale_play)` and never starts that clip.
This 100 ms hard late window matches the phase-one target skew rather than
allowing an old “speak now” command to play later.

DND, block, delete, expiry, target revocation or approach departure is checked
again before T. A non-started target is disarmed. A newly strict setting during
playback uses the active fade-stop behavior and exact cancellation reason.

### 5.4 Duplicate, reconnect and restart behavior

Every target row has a positive monotonically increasing `generation`.
Messages with the same `(transmission_id, generation, type)` are idempotent;
lower generations are ignored; a node rejects play unless the same generation
is locally `ready`. It emits each terminal event once, while the coordinator
also deduplicates by row transition.

Reconnect does not reset expiry, barrier or T. The coordinator may resend a
same-generation prepare or future play. If T's start deadline passed, it marks
the target stale and sends only disarm. Overlay/interrupt work that was never
started is never reconstructed as fresh work with a new acceptance time.

After coordinator restart, persisted work is reconciled before new FIFO work.
A future same-generation schedule may continue. An unverifiable prepared or
active generation is cancelled as `coordinator_restarted`; a past T is stale.
The restart path never changes interrupt into a fallback.

## 6. WebSocket payloads

All fields below are required unless marked optional. Unknown fields are
tolerated at runtime for additive compatibility but rejected by golden
contract tests. The target identity is the authenticated WebSocket binding and
is never present in a client event.

The existing `register.capabilities` array advertises the unique ASCII-sorted
strings `media_clip_v1`, `overlay_mix_v1` and `interrupt_resume_v1`. A node
advertises only behavior it can execute in this build. Unknown additive values
are retained for diagnostics but ignored for v1 decisions; duplicate or
non-string entries reject registration. Reconnect replaces, rather than
unions, the previous connection's capability set.

## 7. DND, blocks and presence

### 7.1 DND layers and ownership

DND modes are `allow_all`, `messages_only`, and `muted_until`.

- `allow_all` adds no DND restriction.
- `messages_only` permits user-authored `voice_clip` and `audio_clip`, but
  suppresses built-in cues, scheduled automation and later track controls.
- `muted_until` suppresses every remote transmission until its coordinator
  timestamp. On expiry that layer becomes `allow_all`.

An explicit `this_pulsar` action authenticated by that same installation is a
local intent and is not suppressed by DND; it cannot address any other target.
Telegram, another installation and every broader audience are remote and must
respect both layers.

Effective DND is the stricter of a node-local layer and an orbit layer;
`muted_until` is stricter than `messages_only`, which is stricter than
`allow_all`. Among two active `muted_until` values, the later timestamp wins.
There is no `force`, `priority`, `emergency` or bypass field in any request.

Ownership boundaries are:

- a local node UI or that exact installation's control credential may mutate
  only its node-local layer;
- a current `primary` may mutate its own orbit layer;
- a verified Telegram primary may mutate only that orbit layer, never an
  individual node's local layer;
- companion/satellite actors and members of another approach orbit cannot
  mutate the orbit layer; and
- no sender, remote control or moderation delivery command may loosen a
  recipient's local DND for the purpose of one transmission.

The downstream presence story may add an audited administrative disable, but
it can only tighten delivery. Local DND is persisted by the node and mirrored
by the coordinator. Orbit DND is coordinator-owned.

`set_dnd` is node to coordinator:

```json
{
  "revision":8,
  "mode":"muted_until",
  "muted_until_coord_ms":1784030400000
}
```

`muted_until_coord_ms` is required only for that mode, must be later than
coordinator now and no more than 30 days ahead. It is forbidden otherwise.
`revision` is a positive node-local monotonic counter. Same revision and same
body is idempotent; same revision with different body or a lower revision is
rejected as `invalid_dnd_revision`. The authenticated connection can update
only itself. The coordinator clock decides expiry; client wall-clock changes
cannot prolong it.

The rejection uses the existing coordinator-to-node `error` envelope payload
`{"code":"invalid_dnd_revision","message":"DND revision is stale or conflicting."}`.

### 7.2 Block boundaries

A recipient actor may create/remove a personal actor or source-orbit block for
itself. A current recipient-orbit `primary` may administer an orbit-scoped
block for that recipient orbit. Approach membership and sender roles grant no
block authority. Only the owner or permitted recipient primary can remove a
block; remote senders and moderators cannot bypass it for delivery.

Blocks are checked at acceptance, before prepare and before scheduled start.
A new block cancels non-started work as `blocked/actor_blocked` or
`blocked/orbit_blocked`; active work uses fade-stop and terminal
`cancelled/sender_blocked`. Removing a block never resurrects a terminal or
missed transmission. Blocked rows do not grant media-byte ACL.

### 7.3 Presence projection

`presence_update` is coordinator to node and is also the acknowledgement of a
valid local DND revision:

```json
{
  "revision":91,
  "generated_at_coord_ms":1784026814000,
  "nodes":[
    {
      "orbit_id":42,
      "slot":"b",
      "online":true,
      "last_seen_at_coord_ms":1784026813800,
      "output_state":"ready",
      "playback_state":"main",
      "dnd_mode":"messages_only",
      "dnd_revision":8,
      "capabilities":["media_clip_v1","overlay_mix_v1","interrupt_resume_v1"],
      "interrupt_resume_ready":true
    }
  ]
}
```

`output_state` is `ready`, `degraded` or `unavailable`.
`playback_state` is `idle`, `main`, `overlay`, `interrupt` or `unknown`.
`dnd_revision` is the accepted node-local revision and makes the update an
unambiguous `set_dnd` acknowledgement.
`dnd_until_coord_ms` is required only when effective mode is `muted_until`.
Offline rows use `output_state=unavailable`, `playback_state=unknown` and
last-known capabilities for display only; they are never capability-decision
inputs. Presence becomes offline after 12 seconds without any authenticated
message. Nodes are sorted by `(orbit_id, slot)` and capabilities by ASCII value
so all three codecs produce deterministic golden JSON. Offline
`interrupt_resume_ready` is false.

Projection is restricted to the caller's own orbit and current pairwise
approach. It contains no actor ID, token, raw connection ID, IP, hostname,
device name, process name, microphone/capture state, audio level, local path or
media URL. Human orbit/approach labels are joined by the authorized read model,
not smuggled in from a node.

## 8. Telegram, history and compatibility mapping

- Telegram calls the same create service with a verified actor context; it
  cannot supply `accepted_at`, origin identity, force/bypass flags or raw target
  rows.
- A ready legacy Telegram voice immediately creates its existing
  `after_current` default. A later inline action may replace it only under the
  separately frozen
  [`p1-history-presence-telegram-v1`](p1-history-presence-telegram-contract-v1.md)
  race contract and receives a new `accepted_at`.
- Bot/UI labels always show requested and effective delivery. Automatic
  overlay downgrade is not rendered as a successful overlay. Interrupt
  challenge is a pending choice, not a transmission or receipt.
- History uses the exact aggregate and target enums above. It may localize
  labels but never map `missed_*`, `blocked`, `failed`, `cancelled` or `expired`
  to `played`.
- Legacy `play_voice` and `solo_voice` remain valid. Automatic overlay
  downgrade and confirmed after-current fallback enter the existing Session
  FSM as one whole media element; the new overlay controller does not send a
  subset via the legacy path.
- Receipt/history retention is 30 days by default. Media delete/expiry removes
  playback and byte actions while leaving content-free delivery evidence.
