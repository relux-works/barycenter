# Часть I. Система

## 1. Назначение и рамки

Система для двоих: единая музыкальная сессия Spotify, звучащая одновременно в двух домах (разные города), с возможностью отправлять друг другу голосовые вставки, которые проигрываются в общий эфир строго после окончания текущего трека.

Что система делает:

1. Режим shared: оба дома слышат один и тот же поток (одинаковые треки, одинаковая позиция, рассинхрон не более 150 мс после калибровки). Очередью управляют оба через Telegram-бота.
2. Голосовые вставки: голосовое сообщение, отправленное боту, проходит обработку (компрессия, выравнивание громкости) и проигрывается в обоих домах после окончания текущего трека. Вариант "лично": играет только у адресата, у отправителя на это время пауза (синхронизация сохраняется).
3. Режим solo: каждый слушает своё со своего телефона (нода видна как обычное устройство Spotify Connect). Доступна команда inject: поставить трек в очередь партнёру. Голосовые вставки работают так же: на ближайшей границе трека у адресата.

Жёсткие ограничения (не обсуждаются на этапе реализации):

- Каждый дом воспроизводит звук через собственный Premium-аккаунт Spotify. Аудио между домами не передаётся ни в каком виде: по сети ходят только управляющие сообщения и файлы голосовых вставок.
- TTS отсутствует. Вставки: только живые голосовые из Telegram.
- Ровно два дома, ровно два пользователя. Масштабирование не закладывается.

## 2. Ключевые решения и их обоснование

Эти решения приняты на этапе проектирования. Менять их в ходе реализации нельзя без согласования с заказчиком.

| Решение | Обоснование |
|---|---|
| Нода в каждом доме: mac (mini или аналог), а не iPhone | iOS не отдаёт PCM-поток Spotify наружу, микширование и вставки на iPhone невозможны. macOS даёт нативный вывод на AirPlay-колонку |
| Плеер: go-librespot (headless Spotify Connect клиент) | Ставится через brew на macOS, имеет локальный HTTP+WebSocket API для управления и событий, поддерживает вывод сырого PCM в именованный пайп (audio_backend: pipe). Требует Premium. Нода видна в приложении Spotify как обычная колонка |
| Микшер: собственное Swift-приложение (NodeApp) на AVAudioEngine | Полный контроль над аудиографом: музыка из FIFO + голосовые вставки + громкость. Один кодбейс на оба дома, так как ноды идентичны |
| Доставка на колонки: режим direct (по умолчанию) либо Airfoil (v1.3) | direct: NodeApp играет в системный выход macOS, которым выбрано одно устройство дома (AirPlay/Bluetooth/провод); NodeApp мониторит и возвращает выбранное устройство (DirectOutputMonitor), деградация на встроенные динамики происходит средствами macOS. airfoil (флаг airfoil.enabled): 1..N колонок в синхроне через Airfoil/AppleScript — только на macOS 15 Sequoia (на macOS 26 Airfoil 5.12.6 непригоден: дропауты, подтверждено живыми пробами 2026-07-03; скриптовая установка app-source в 5.12.6 сломана — источник выбирается в GUI при сетапе). NodeApp в обоих режимах остаётся единственным микшером |
| В режиме shared координатор ведёт воспроизведение потреково | Координатор командует загрузку и старт каждого элемента очереди на обеих нодах. Это даёт синхронизацию на каждой границе и делает вставку голосового тривиальной: это просто элемент очереди. Цена: пауза 1-2 с между треками (приемлемо, звучит как радио) |
| Сеть: Tailscale mesh (2 мака + VPS) | Нулевая настройка NAT, шифрованный транспорт, SSH-доступ к удалённому маку. Никаких публичных портов |
| Голосовые обрабатываются один раз на координаторе (ffmpeg) | Оба дома получают идентичный файл с уже выровненной громкостью. Ноды остаются тупыми плеерами |
| Часы: системный NTP macOS + поправка через WS-пинг координатора | Достаточно для цели <= 150 мс без выделенной инфраструктуры точного времени |

Правовой контекст: go-librespot и librespot-семейство: неофициальные клиенты, формально это серая зона относительно ToS Spotify. Использование строго личное, два оплаченных Premium-аккаунта, аудио не ретранслируется. Заказчик риск принимает.

## 3. Архитектура

### 3.1 Компоненты

```
                    +-----------------+
                    |     Spotify     |
                    | (два аккаунта)  |
                    +--------+--------+
              стрим A |            | стрим B
                      v            v
   Дом A ......................  Дом B ......................
   :  +--------------------+  :  :  +--------------------+  :
   :  |   go-librespot     |  :  :  |   go-librespot     |  :
   :  |  (аккаунт A, pipe) |  :  :  |  (аккаунт B, pipe) |  :
   :  +---------+----------+  :  :  +---------+----------+  :
   :            | FIFO (PCM)  :  :            | FIFO (PCM)  :
   :            v             :  :            v             :
   :  +--------------------+  :  :  +--------------------+  :
   :  |  NodeApp (Swift)   |  :  :  |  NodeApp (Swift)   |  :
   :  |  AVAudioEngine     |  :  :  |  AVAudioEngine     |  :
   :  +---------+----------+  :  :  +---------+----------+  :
   :            v             :  :            v             :
   :   Airfoil -> колонки     :  :   Airfoil -> колонки     :
   :..........................:  :..........................:
                ^                             ^
                |  WebSocket (tailnet)        |
                +--------------+--------------+
                               |
                    +----------+----------+
                    |     Координатор     |
                    |  (VPS в tailnet)    |
                    |  сессия, очередь,   |
                    |  планировщик,       |
                    |  ffmpeg, TG-бот     |
                    +----------+----------+
                               |
                        Telegram Bot API
                               |
                      чат: пользователи A и B
```

### 3.2 Распределение ответственности

| Компонент | Отвечает за | НЕ отвечает за |
|---|---|---|
| go-librespot (x2) | Авторизация в Spotify, получение и декодирование стрима, выдача PCM в FIFO, локальный API управления плеером | Микширование, сеть между домами |
| NodeApp (x2) | Супервизия go-librespot, аудиограф (музыка + вставки + громкость), управление Airfoil (источник, колонки, статус), применение latency offset, связь с координатором, локальное поведение в solo | Логика сессии, очередь, обработка медиа |
| Airfoil (x2) | Захват звука NodeApp, доставка на 1..N колонок дома, синхронность колонок между собой внутри дома, per-speaker громкость и подстройка задержки | Микширование, вставки, логика сессии |
| Координатор (x1) | State-машина сессии, очередь элементов, синхронизация стартов, Telegram-бот, обработка и раздача голосовых, журнал | Воспроизведение звука |
| Tailscale | Транспорт, адресация (MagicDNS), SSH к удалённому маку | Прикладная авторизация (есть свои токены) |

### 3.3 Потоки данных

1. Аудио Spotify: облако -> go-librespot -> FIFO -> NodeApp -> Airfoil -> колонки дома. Не покидает дом.
2. Управление: координатор <-> NodeApp, WebSocket поверх tailnet, JSON (глава 8).
3. Голосовые: Telegram -> координатор (скачивание файла) -> ffmpeg -> WAV в media-хранилище -> ноды скачивают по HTTP GET с токеном (тот же процесс координатора, bind только на tailnet-адрес).
4. Команды пользователей: Telegram -> бот (long polling, исходящее соединение с VPS; входящих публичных портов нет).

## 4. Режимы работы и сценарии

### 4.1 Режим shared (основной)

Координатор владеет очередью элементов и ведёт воспроизведение потреково:

1. Берёт следующий элемент очереди.
2. Если элемент track: рассылает обеим нодам load (uri, position). Ноды загружают трек в паузе и отвечают ready.
3. Когда обе ноды ready: рассылает resume_at с меткой времени T по часам координатора. Каждая нода стартует в момент T с поправкой на свой clock offset и минус свой output_latency_offset_ms.
4. Играет. Ноды шлют heartbeat с позицией. По событию окончания трека от нод координатор переходит к п.1.
5. Если элемент voice: рассылает play_voice целевым нодам (файл по URL). Нецелевая нода получает wait той же длительности (тишина). По завершении: п.1.

Пауза 1-2 с между треками из-за цикла load/ready/resume_at: ожидаемое поведение, не дефект.

Сценарии пользователя (shared):
- Отправил ссылку на трек в чат: трек добавлен в конец очереди.
- /playnow <ссылка>: текущий элемент останавливается (fade 300 мс), новый стартует по обычному циклу.
- Отправил голосовое: элемент voice добавлен в очередь сразу после текущего трека (перед остальными элементами очереди).
- Голосовое с подписью "лично": target = партнёр, у отправителя тишина той же длительности.
- /pause, /resume, /skip: применяются к обеим нодам синхронно.

### 4.2 Режим solo

Координатор перестаёт вести воспроизведение. Каждый пользователь управляет своей нодой из своего приложения Spotify (нода видна как Connect-устройство). NodeApp продолжает слать состояние координатору (для /now и /status).

- /inject <ссылка> [цель]: трек ставится в очередь Spotify целевой ноды через локальный API go-librespot (POST /player/add_to_queue: наличие подтверждено по OpenAPI-спеке демона 0.7.4, финальный живой вызов в остатке spike). Fallback "перебить на границе" не требуется.
- Голосовое в solo: NodeApp целевой ноды сам ловит границу трека: при остатке <= 400 мс ставит librespot на паузу, проигрывает вставку, затем командует next. Потеря хвоста трека до 400 мс: принятое поведение.

### 4.3 Переключение режимов

/mode shared: координатор забирает управление. Текущее воспроизведение нод останавливается, стартует общая очередь (пустая очередь: состояние IDLE, в чат подсказка прислать ссылку).
/mode solo: координатор останавливает общую сессию (позиция очереди сохраняется), ноды переходят в свободное плавание.

### 4.4 Деградация

- Нода офлайн > 12 с в shared: координатор ставит сессию на паузу (вторая нода получает pause), сообщение в чат. После реконнекта: /resume продолжает текущий элемент с сохранённой позиции.
- Нода офлайн в solo: сообщение в чат, вторая нода не затрагивается.
- Трек недоступен на одном из аккаунтов (region mismatch): нода отвечает error на load, координатор пропускает элемент, сообщение в чат с указанием причины.
- Колонка отвалилась от Airfoil: NodeApp пытается переподключить её (AppleScript connect с бэкоффом), шлёт degraded с перечнем колонок, сообщение в чат. Если не осталось ни одной подключённой: аварийно подключается локальный выход "Computer".

## 5. Модель данных и потоки

### 5.1 Элемент очереди

Единица эфира. Всё, что звучит, это элемент.

```json
{
  "id": "el_01J...",
  "kind": "track | voice",
  "uri": "spotify:track:...",
  "media_id": "m_01J...",
  "title": "для журнала и /queue",
  "duration_ms": 214000,
  "requested_by": "a | b",
  "target": "both | a | b",
  "created_at": 1751500000000
}
```

Для kind=track заполняется uri, для kind=voice: media_id и duration_ms (после обработки ffmpeg). target для треков всегда both; для voice: both либо одна нода.

### 5.2 Состояние сессии (владеет координатор)

```json
{
  "mode": "shared | solo",
  "state": "idle | loading | armed | playing | voice | paused | degraded",
  "current": { "element_id": "...", "started_at": 1751500000000, "position_ms": 63000 },
  "queue": ["el_...", "el_..."],
  "nodes": {
    "a": { "online": true, "position_ms": 63012, "volume": 80, "degraded": false },
    "b": { "online": true, "position_ms": 62998, "volume": 65, "degraded": false }
  }
}
```

### 5.3 Хранилище координатора

SQLite, один файл. Таблицы:

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| elements | Журнал всех элементов (история эфира) | id, kind, uri/media_id, requested_by, target, created_at, played_at, status |
| media | Голосовые файлы | id, tg_file_id, duration_ms, path_wav, loudnorm_json, created_at, expires_at |
| settings | Ключ-значение (mode, офсеты, громкости) | key, value |
| events | Журнал событий для отладки | ts, source, type, payload |

Файлы голосовых: каталог media_dir, имя файла = media_id + .wav. Исходный ogg удаляется после успешной обработки. WAV хранится 30 дней, чистка по expires_at ежедневно.

### 5.4 Время

Все метки времени: UTC, миллисекунды, int64. Эталон: часы координатора. Ноды вычисляют clock_offset по WS-пингу (глава 8.5) и переводят resume_at в локальное время. Поверх этого каждая нода вычитает свой output_latency_offset_ms (задержка тракта NodeApp -> AirPlay -> звук в комнате, измеряется вручную, глава 14).

# Часть II. Разработка

## 6. NodeApp (Swift, macOS)

Отдельный репозиторий-модуль `node-app/` (SwiftPM, executable target). Один бинарь, деплоится на оба мака без изменений, вся специфика дома в конфиге.

### 6.1 Требования к окружению

- macOS 14+, Apple Silicon.
- Swift 5.10+, только SwiftPM, без Xcode-проекта. Зависимости: стандартные фреймворки (AVFAudio, CoreAudio, Network или URLSession для WS), допускается одна библиотека для YAML-конфига.
- Работает как LaunchAgent в пользовательской сессии (не LaunchDaemon: CoreAudio и AirPlay требуют пользовательского контекста). Автологин пользователя обязателен (глава 12).
- Без GUI. Управление: конфиг + сигналы + логи. Опциональный подкомандный CLI (`nodeapp status`) приветствуется, но не обязателен.

### 6.2 Обязанности

1. Супервизия go-librespot: запуск дочерним процессом, рестарт с экспоненциальным бэкоффом (1, 2, 4, ... максимум 30 с), рендер его config.yml из своего конфига при старте (порт API, имя устройства, путь FIFO, формат, external_volume: true). Для Spotify Connect discovery NodeApp передаёт дочернему процессу `PULSAR_ZEROCONF_HOST` из macOS `LocalHostName`, а бандлируемый fork go-librespot использует это имя как DNS-SD SRV target; иначе stale kernel hostname может рекламировать неразрешимый `*.local`.
2. Клиент локального API go-librespot: подписка на WebSocket-события /events (will_play, playing, not_playing, stopped, metadata), команды play/pause/resume/seek/next/add_to_queue/volume через HTTP (по OpenAPI-спеке демона, зафиксировано на 0.7.4). До логина GET /status может возвращать пустое тело: клиент обязан это переживать. Остаточные живые проверки: глава 20.
3. Аудиограф (6.3).
4. WebSocket-клиент координатора: регистрация, приём команд, отправка состояния и событий (протокол: глава 8). Реконнект с бэкоффом, при реконнекте полный снапшот состояния.
5. Исполнение команд координатора: load (загрузить трек в паузе с позиции), resume_at (стартовать в момент T), pause, seek, play_voice, wait, set_volume, set_mode.
6. Локальная логика solo: перехват границы трека для голосовой вставки (4.2), исполнение inject.
7. Применение output_latency_offset_ms ко всем запланированным стартам.
8. Доставка на колонки (v1.3, два режима):
   - direct (airfoil.enabled: false, по умолчанию): модуль DirectOutputMonitor — раз в poll_s читает имя текущего системного выхода (CoreAudio); при заданном audio.output_device сверяет и при несовпадении пытается вернуть устройство (set default output, бэкофф), degraded в heartbeat. Выбор устройства при сетапе: Control Center (глава 14).
   - airfoil (airfoil.enabled: true, только macOS 15): модуль AirfoilBridge, AppleScript через osascript-подпроцессы (NSAppleScript вне main thread в CLI виснет — spike): запуск приложения при старте, подключение колонок из конфига, опрос connected/volume раз в poll_s, переподключение отвалившихся с бэкоффом, аварийный "Computer", деградация (4.4). Источник (NodeApp или System-Wide Audio + mute локального выхода) выбирается в GUI при сетапе: скриптовый сеттер app-source в Airfoil 5.12.6 сломан (spike S5); словарь: connect to / disconnect from.

### 6.3 Аудиограф

```
FIFO (f32le 44100 stereo interleaved)
   -> reader thread -> ring buffer (ёмкость 1.0 с)
        -> AVAudioSourceNode ("музыка")
                                \
                                 -> mainMixerNode -> outputNode -> AirPlay-устройство
                                /
AVAudioPlayerNode ("вставки") --
   (WAV-файлы голосовых)
```

Требования:

- Формат тракта: 44100 Гц, 2 канала, Float32. go-librespot настраивается на `audio_output_pipe_format: f32le`, конверсий на входе быть не должно. Если librespot отдаёт трек с иной частотой (проверка в остатке spike): включить AVAudioConverter, но базовый путь без ресемплинга. Ресемплинг под выходное устройство (например 48 кГц) движок делает сам: ручной конвертер на выходе не нужен (подтверждено в spike).
- FIFO читается выделенным потоком блокирующим read в ring buffer (lock-free SPSC). При полном ринге ридер обязан блокироваться и не читать из пайпа: backpressure через буфер пайпа ядра естественно тормозит писателя. Дроп данных запрещён (урок spike: наивный ридер терял 4 секунды из 5 на burst-префилле). Блокирующий open пайпа до появления писателя: штатное состояние ожидания (демон открывает пайп лениво, порядок запуска свободный). EOF: переоткрыть. Render-колбэк AVAudioSourceNode только копирует из ринга, без локов, аллокаций и I/O.
- Underrun (буфер пуст, например librespot на паузе или упал): отдавать тишину, инкрементировать счётчик underruns, не останавливать движок. Пайп закрыт: переоткрыть, продолжить с тишиной.
- Старт по времени: якорь старта: момент подачи resume в librespot (T_local). Prefill ринга перед стартом не требуется и не ожидается: в паузе librespot данных в пайп не пишет (проверка в остатке spike). Задержка resume -> первые сэмплы входит в калибруемый offset.
- Учёт ринга в таймингах: позиция librespot опережает звук в комнате на заполнение ринга (до ~1 с при полном ринге). NodeApp ведёт audible_position = librespot_position - ring_fill_ms и использует её в heartbeat и в solo-перехвате границы (4.2): порог 400 мс считается от аудируемого остатка.
- Громкость: применяется на ветке музыки и вставок раздельно? Нет: общий volume на mainMixerNode, диапазон 0..100, маппинг amplitude = (v/100)^2, дефолт 80. Вставки идут с собственным фиксированным гейном 1.0 (файлы уже нормализованы).
- Выход: движок играет в дефолтный выход macOS; доставку до колонок делает Airfoil, захватывая NodeApp как application source. Требование сборки: NodeApp упаковывается как минимальный .app bundle (application source в Airfoil задаётся POSIX-путём до приложения; захват голого CLI-бинаря не гарантирован, проверка в spike).
- Роли громкостей: master-громкость (/vol) живёт в mainMixerNode движка; per-speaker громкости в Airfoil: статический баланс между колонками дома, выставляется при сетапе (по умолчанию 1.0) и NodeApp их не трогает (только читает для heartbeat).
- Синхронность колонок внутри дома: забота Airfoil (при слышимом рассинхроне: per-speaker подстройка Sync в Advanced Speaker Options при сетапе). Междомовая синхронность: наш output_latency_offset_ms, в который теперь входит и буферизация Airfoil.
- Silence Monitor в Airfoil обязан быть выключен (иначе паузы эфира будут отключать колонки).

Механика load/resume для трека (shared):

1. load: двухшагово, поля позиции у play нет: POST /player/play {uri, paused: true}, затем при position_ms > 0: POST /player/seek {position, relative: false}. Ring buffer очищается (безопасно: предыдущий элемент к этому моменту дозвучал, см. п.5). Ответ ready координатору: когда статус/событие подтверждает загруженное запаузенное состояние после обоих шагов (работа seek в паузе: живое подтверждение в остатке spike).
2. resume_at(T): NodeApp вычисляет T_local = T + clock_offset - output_latency_offset_ms и взводит таймер. В момент T_local командует librespot resume. Данные начинают течь в FIFO, source node их отдаёт.
3. Важно: задержка между командой resume и звуком в комнате (внутренняя буферизация librespot, движка и Airfoil) входит в общий тракт и калибруется одним общим output_latency_offset_ms на ноду. Отдельно по звеньям не измеряется.
4. started отправляется координатору с фактическим временем первого ненулевого блока из FIFO (пересчитанным в часы координатора): координатор использует это для диагностики рассинхрона.
5. ended (reason: eof) отправляется, когда librespot сообщил конец трека (not_playing/stopped) И ринг осушён: хвост размером с заполнение ринга должен дозвучать. Иначе следующий load срежет до секунды каждого трека.

Механика play_voice:

1. NodeApp скачивает WAV по file_url во временный каталог (если ещё нет в кэше по media_id).
2. Планирует AVAudioPlayerNode: старт немедленно (в shared музыка уже кончилась) либо по T из команды, если координатор прислал синхронизированный старт вставки (использовать тот же механизм T_local).
3. По окончании файла: voice_ended координатору, файл остаётся в кэше (LRU, 50 файлов).

Команда wait(duration_ms): тишина, по истечении wait_ended. Реализация: таймер, движок продолжает играть тишину из пустого source node.

### 6.6 Поведение при сбоях

| Сбой | Поведение |
|---|---|
| go-librespot умер | Рестарт с бэкоффом; координатору error(librespot_restart); в shared координатор перезапустит текущий элемент через обычный цикл load/resume_at |
| Пропал WS координатора | Реконнект с бэкоффом; воспроизведение НЕ останавливается (доигрывает текущее); после реконнекта снапшот состояния, координатор решает, что делать |
| Колонка отвалилась от Airfoil | Переподключение AppleScript-командой connect с бэкоффом; degraded в heartbeat; ни одной живой колонки: подключить локальный выход "Computer"; уведомление в чат делает координатор |
| Airfoil не запущен или умер | NodeApp запускает его, заново выставляет источник и подключает колонки из конфига |
| Underruns подряд > 3 с | error(audio_starvation) координатору, попытка мягкого рестарта librespot |
| Мак перезагрузился | launchd поднимает NodeApp, тот поднимает librespot, регистрируется у координатора; воспроизведение возобновляется командой пользователя |

## 7. Координатор

Модуль `coordinator/`. Рекомендуемый стек: Go 1.22+ (один статический бинарь, простой деплой). Допустимая альтернатива: Python 3.12 + FastAPI при полном сохранении протокола и поведения. Хранилище: SQLite (5.3). Развёртывание: systemd на VPS внутри tailnet (глава 16). Допустимо разместить на одном из маков (launchd), конфиг не меняется; базовый вариант: VPS.

### 7.1 Внутренние модули

| Модуль | Ответственность |
|---|---|
| ws-hub | WebSocket-сервер для нод: аутентификация по токену, реестр подключений, доставка сообщений, детект офлайна (нет heartbeat 12 с) |
| session | State-машина сессии (7.2), очередь элементов, персист состояния в SQLite (переживает рестарт) |
| scheduler | Расчёт T для resume_at: T = now + max(RTT_a, RTT_b) * 2 + 500 мс; таймауты ready (8 с, 1 ретрай, затем skip элемента + сообщение в чат) |
| tg-bot | Long polling Telegram Bot API, парсинг команд (глава 9), allowlist из двух user_id, маппинг user -> дом |
| media | Скачивание голосовых из Telegram, запуск ffmpeg (глава 10), учёт в таблице media, ретеншн-чистка |
| http-media | GET /media/{id}.wav c заголовком Authorization: Bearer <токен ноды>; bind только на tailscale-адрес |
| status | Сборка ответов /now и /status из последних heartbeat |

### 7.2 State-машина (режим shared)

Состояния: IDLE, LOADING, ARMED, PLAYING, VOICE, PAUSED, DEGRADED.

| Из | Событие | В | Действия |
|---|---|---|---|
| IDLE | очередь непуста | LOADING | взять элемент; track: load обеим; voice: сразу в VOICE |
| LOADING | ready от всех целевых нод | ARMED | разослать resume_at(T) |
| LOADING | таймаут ready 8 с | LOADING | 1 ретрай load; повторный таймаут: skip, сообщение в чат, к следующему элементу |
| ARMED | started от обеих | PLAYING | зафиксировать фактический рассинхрон в журнал |
| PLAYING | ended от обеих (или ended одной + позиция второй >= duration - 1 с) | LOADING/VOICE | следующий элемент |
| PLAYING | /pause | PAUSED | pause обеим, сохранить позицию |
| PAUSED | /resume | LOADING | load с сохранённой позиции, далее обычный цикл |
| PLAYING | /skip | LOADING | pause обеим, следующий элемент |
| VOICE | voice_ended (и wait_ended нецелевой) | LOADING | следующий элемент |
| любое | нода офлайн 12 с | DEGRADED | pause живой ноде, сообщение в чат |
| DEGRADED | нода вернулась | PAUSED | сообщение в чат, ждать /resume |
| любое | /mode solo | (solo) | stop обеим, сохранить очередь и позицию |

Идемпотентность: все команды нодам несут element_id; нода игнорирует resume_at/pause для неактуального element_id. Ретраи безопасны.

Восстановление после рестарта координатора: состояние и очередь читаются из SQLite; если был PLAYING, переход в PAUSED с сообщением в чат (позиция берётся из первого heartbeat нод).

### 7.3 Правила очереди

- Ссылка на трек: в конец очереди.
- Голосовое: вставляется сразу после текущего элемента (перед остальной очередью). Несколько голосовых: в порядке получения.
- /playnow: текущий элемент останавливается (нодам pause с fade 300 мс на ветке музыки), новый элемент в голову очереди, цикл LOADING.
- Дубликаты ссылок допускаются (не фильтруем).
- Поддерживаемые ссылки в MVP: track. Ссылки на плейлист/альбом: ответ бота "пока только треки" (раскрытие плейлистов: фаза 2, глава 19).

### 7.4 Конфиг координатора

Файл `/etc/duet/coordinator.yml`, пример: приложение A. Ключевое: listen-адрес (tailscale IP:8080), токены нод, telegram.bot_token, telegram.users (map user_id -> a|b), media_dir, db_path, тайминги (ready_timeout_s: 8, start_margin_extra_ms: 500, offline_after_s: 12, near_end_ms: 400), ffmpeg-пресет (глава 10).

## 8. Протокол координатор-нода

WebSocket, текстовые фреймы, JSON. Одно соединение на ноду, инициатор: нода.

### 8.1 Конверт

```json
{ "v": 1, "id": "msg_01J...", "ts": 1751500000000, "type": "resume_at", "payload": { } }
```

v: версия протокола (несовпадение мажора: нода отключается с ошибкой в лог и чат). id: уникален у отправителя, используется в логах. ts: часы отправителя, мс UTC.

### 8.2 Аутентификация

Первое сообщение ноды: register. Неверный токен: координатор закрывает соединение кодом 4401. Повторное подключение той же node_id: старое соединение закрывается (last-write-wins).

### 8.3 Каталог сообщений: координатор -> нода

| type | payload | Семантика |
|---|---|---|
| welcome | { session_snapshot } | Ответ на register: текущий режим, элемент, громкость этой ноды |
| load | { element_id, uri, position_ms } | Загрузить трек в паузе. Ответ: ready или error |
| resume_at | { element_id, t_coord_ms } | Стартовать загруженный элемент в момент T (часы координатора) |
| pause | { element_id, fade_ms } | Пауза (fade_ms >= 0, 0 = мгновенно) |
| seek | { element_id, position_ms } | Перемотка (используется при /resume после паузы: через load, seek в MVP опционален) |
| play_voice | { element_id, file_url, t_coord_ms? } | Скачать и проиграть вставку; t_coord_ms задан: стартовать по времени, нет: немедленно |
| wait | { element_id, duration_ms } | Тишина заданной длительности (нецелевая нода при личной вставке) |
| set_volume | { volume } | 0..100 на mainMixer |
| set_mode | { mode } | shared: перейти под управление; solo: свободное плавание |
| stop | { } | Полная остановка воспроизведения (смена режима) |
| solo_inject | { uri } | Только в solo: поставить трек в очередь Spotify этой ноды (POST /player/add_to_queue) |
| solo_voice | { element_id, file_url } | Только в solo: вставка на ближайшей границе трека (механика 4.2) |
| pong | { t1, t2, t3 } | Ответ на ping ноды: метки времени для расчёта offset (8.5) |

### 8.4 Каталог сообщений: нода -> координатор

| type | payload | Семантика |
|---|---|---|
| register | { node_id, token, app_version, librespot_version } | Первое сообщение |
| state | { playback, uri, position_ms, volume, degraded, underruns, rtt_ms, speakers: [{name, connected}] } | Полный снапшот: после welcome, при любом изменении, и как heartbeat раз в 5 с. rtt_ms: последний замер (8.5), используется планировщиком |
| ready | { element_id } | Трек загружен, готов к resume_at |
| started | { element_id, t_first_sample_coord_ms } | Фактический момент первого звука |
| ended | { element_id, reason: "eof" or "skipped" or "error" } | Элемент закончился |
| voice_started / voice_ended / wait_ended | { element_id } | Жизненный цикл вставки/тишины |
| error | { code, message, element_id? } | Коды: load_failed, track_unavailable, media_download_failed, audio_starvation, librespot_restart, device_lost |
| ping | { t1 } | Раз в 10 с: инициирует обмен метками времени (8.5) |

### 8.5 Синхронизация часов

Инициатор: нода, раз в 10 с. Нода шлёт ping с меткой t1 (свои часы). Координатор фиксирует t2 при приёме и t3 при отправке pong (свои часы) и возвращает все три метки. Нода фиксирует t4 при приёме. Далее классика NTP:

- rtt = (t4 - t1) - (t3 - t2)
- clock_offset = ((t1 - t2) + (t4 - t3)) / 2: насколько часы ноды впереди часов координатора. Знак согласован с 6.3: T_local = T_coord + clock_offset.

Требования: скользящее сглаживание (EMA, alpha 0.2), отбрасывание замеров с rtt > 3x медианы последних десяти, целевая точность итогового clock_offset +-20 мс на стабильном tailnet. Последний rtt нода сообщает в heartbeat: планировщик координатора использует max(rtt_a, rtt_b) при расчёте T (7.1).

### 8.6 Гарантии и переподключение

- Доставка: не гарантируется. Гарантию даёт цикл команда -> подтверждение с ретраями на стороне координатора (ready_timeout, идемпотентность по element_id).
- При реконнекте нода получает welcome со снапшотом и приводит себя к нему: несовпадение element_id: нода останавливает лишнее и ждёт команд.
- Сообщения неизвестного type игнорируются с warn-логом (совместимость вперёд).

### 8.7 Контрактные тесты

В репозитории: каталог golden-файлов JSON (по одному на тип сообщения) и тесты сериализации в обоих компонентах против одних и тех же файлов. Изменение протокола = изменение golden-файлов в том же PR.

## 9. Telegram-интерфейс

Один приватный чат-группа: два пользователя + бот, либо два личных чата с ботом (решение при сетапе; функционально идентично, бот шлёт уведомления в оба контекста... базовый вариант: одна группа на троих, все уведомления туда).

### 9.1 Команды

| Ввод | Режим | Действие |
|---|---|---|
| ссылка на трек Spotify (просто сообщением) | shared | Добавить в очередь. Ответ: название и позиция в очереди |
| /playnow <ссылка> | shared | Немедленно (7.3) |
| голосовое сообщение | оба | Обработать, поставить вставку: shared: после текущего трека, обоим; solo: на ближайшей границе у партнёра |
| голосовое с подписью "лично" | shared | Вставка только партнёру, отправителю wait |
| /queue | shared | Показать очередь (номер, тип, название, кто добавил) |
| /cancel <номер> | shared | Удалить элемент из очереди |
| /skip | shared | Пропустить текущий |
| /pause, /resume | shared | Пауза и продолжение синхронно |
| /vol <0-100> [a или b] | оба | Громкость; без аргумента дома: своя нода |
| /inject <ссылка> [цель] | solo | Трек в очередь партнёру (по умолчанию) или себе/обоим |
| /mode shared, /mode solo | оба | Переключение режима (4.3) |
| /now | оба | Что сейчас играет (по нодам в solo, общий элемент в shared) |
| /status | оба | Онлайн нод, режим, позиции, рассинхрон последнего старта, degraded-флаги, версии |
| /sync | shared | Принудительный перезапуск текущего элемента с текущей позиции (пересинхронизация) |
| /offset <a или b> <мс> | оба | Установить output_latency_offset_ms ноды (глава 14), сохраняется в settings и пушится ноде |
| /offset_test | оба | Прогнать серию из 5 синхронных кликов на обеих нодах (для калибровки на созвоне) |

Разбор ссылок: принимать open.spotify.com/track/... и spotify:track:...; intl-пути и query-параметры отбрасывать. Название трека для ответов бота: из метаданных, которые нода/librespot сообщает после load (отдельного похода в Web API в MVP нет; до load в ответе бота допустимо показывать только id).

### 9.2 Правила доступа

- Обрабатываются только сообщения от двух user_id из конфига. Остальное: молча игнорировать.
- Ошибки пользователю: короткие человеческие сообщения ("трек недоступен на аккаунте B, пропустил", "голосовое длиннее 3 минут, не возьму").
- Уведомления бота: старт сессии, деградация/восстановление нод, пропуск элемента с причиной, смена режима. Без спама: не сообщать о каждом треке.

## 10. Медиа-пайплайн голосовых вставок

### 10.1 Приём

1. Update с voice из Telegram: скачать файл (getFile) во временный каталог.
2. Валидация: длительность <= 180 с (из метаданных Telegram; больше: отказ сообщением), размер <= 20 МБ.
3. Создать запись media, запустить обработку.

### 10.2 Обработка (ffmpeg)

Базовая команда (пресет default, значения в конфиге координатора):

```
ffmpeg -y -i in.oga \
  -af "highpass=f=90, acompressor=threshold=-20dB:ratio=3:attack=10:release=180:makeup=4, loudnorm=I=-14:TP=-1.5:LRA=11:print_format=json" \
  -ar 44100 -ac 2 -c:a pcm_s16le out.wav
```

- Цель по громкости: I = -14 LUFS, как у музыки после нормализации go-librespot (его штатный таргет по стандарту Spotify). Вставка не должна выбиваться из эфира по уровню более чем на +-2 LU.
- Двухпроходный loudnorm не требуется (короткие файлы, допуск +-2 LU); JSON-отчёт loudnorm сохранять в media.loudnorm_json.
- Опциональный пресет radio (флаг в конфиге, по умолчанию выключен): дополнительно equalizer=f=4500:t=q:w=1:g=2 и лёгкий деэссер. Включается на вкус после MVP.
- Выход: WAV PCM s16le 44100/stereo (моно-источник разворачивается в стерео), длительность записывается в media.duration_ms.
- Ошибка ffmpeg: сообщение в чат, запись media со статусом failed, исходник сохранить для разбора.

### 10.3 Раздача нодам

GET /media/{media_id}.wav, заголовок Authorization: Bearer <токен ноды>, только tailnet-адрес. 404 после истечения expires_at. Нода кэширует по media_id (6.3).

# Часть III. Ручной сетап

Всё в этой части делается руками один раз (или при замене железа). Каждая глава: чеклист с проверкой в конце.

## 11. Tailscale

1. Создать tailnet (аккаунт Tailscale), включить MagicDNS.
2. Установить Tailscale на: мак A, мак B, VPS. Залогинить все три машины в один tailnet.
3. Имена машин: node-a, node-b, coord (переименовать в админке; эти имена используются в конфигах).
4. Отключить key expiry для всех трёх машин (админка -> машина -> Disable key expiry). Иначе через 180 дней всё молча отвалится.
5. Включить Tailscale SSH на обоих маках (tailscale set --ssh). Проверить с рабочей машины заказчика: ssh <user>@node-b проходит.
6. ACL (админка): минимум: разрешить node-a, node-b -> coord:8080; coord -> node-a, node-b (ответный трафик в рамках соединений нод); admin-устройства заказчика -> ssh на все. Если возиться с ACL не хочется: дефолтный allow-all внутри личного tailnet приемлем (риск-решение заказчика).

Проверка: с мака A выполняется `curl http://coord:8080/healthz` (после деплоя координатора), ping node-b по имени работает.

## 12. Подготовка маков

Одинаково для обоих домов.

1. Чистый пользователь (например duet), автологин включён (Настройки -> Пользователи -> Автоматический вход). Следствие: FileVault должен быть выключен. Это осознанный размен: headless-аудио требует живой пользовательской сессии.
2. Питание: System Settings -> Energy: не засыпать, включаться после сбоя питания. Дополнительно в терминале: `sudo pmset -a sleep 0 disksleep 0 displaysleep 5 autorestart 1`.
3. Автообновления macOS: автоматическую установку выключить (только уведомления). Обновления ставятся вручную в согласованное время: внезапный ребут = тишина в эфире.
4. Hostname = имя в tailnet (node-a / node-b) для однозначности логов.
5. Screen Sharing: по желанию (Tailscale SSH обычно достаточно).
6. Создать каталоги: `~/duet/` (конфиги, логи), `~/duet/cache/` (кэш вставок).
7. Установить brew (если нет).

Проверка: после `sudo reboot` мак сам логинится в сессию duet-пользователя и доступен по Tailscale SSH.

## 13. go-librespot: установка и первый вход

На каждом маке:

1. `brew install go-librespot` (или бинарь из релизов GitHub, если формулы нет в актуальном brew: зафиксировать способ установки в runbook).
2. Конфиг НЕ писать руками: его рендерит NodeApp (6.2). Но первый вход выполняется до боевого запуска: запустить go-librespot вручную с конфигом из приложения A (credentials: type: zeroconf).
3. Владелец аккаунта этого дома открывает Spotify на своём телефоне (та же Wi-Fi сеть, что и мак), выбирает устройство "Дом A"/"Дом B" в списке устройств: происходит zeroconf-логин, go-librespot сохраняет credentials в свой каталог (`~/Library/Application Support/go-librespot`).
4. Убедиться, что музыка играет (на этом этапе: через дефолтный аудиовыход либо уже в пайп: тогда проверять чтением из FIFO), остановить ручной процесс.

Важно: вход в аккаунт B делает владелец аккаунта B со своего телефона у себя дома. Пароли друг другу не передаются.

Проверка: файл credentials существует; повторный запуск go-librespot подхватывает сессию без логина; `curl http://127.0.0.1:3678/` отвечает JSON с полем playback_ready (штатный health-чек демона).

## 14. Колонки и замер задержки

### 14.0 Режим direct (по умолчанию, v1.3)

1. Подключить/спарить устройство дома (AirPlay-колонка, Bluetooth или провод).
2. Выбрать его выходом в Control Center (или Настройки -> Звук). macOS запомнит выбор.
3. Вписать точное имя устройства в node.yml -> audio.output_device. NodeApp мониторит выход, при отвале возвращает устройство и репортит degraded; замер offset: п. 14.4 без изменений.
4. Замьютить/не использовать встроенные динамики не требуется: direct-режим играет только в выбранное устройство.

### 14.1+ Режим airfoil (airfoil.enabled: true, только macOS 15 Sequoia)

1. Установить Airfoil (Rogue Amoeba) на оба мака, купить лицензию на каждый (в trial-режиме Airfoil накладывает шум после 10 минут: для боевой работы непригоден). Разрешить установку ACE (Audio Capture Engine): системное расширение Rogue Amoeba, требует подтверждений в System Settings и перезагрузки, у вендора есть пошаговая инструкция.
2. В Airfoil: выключить Silence Monitor; подключить колонки дома, убедиться, что все играют; при слышимом рассинхроне между колонками одного дома подстроить per-speaker Sync (Advanced Speaker Options). Имена колонок как в списке Airfoil вписать в node.yml (airfoil.speakers).
3. При первом запуске NodeApp разрешить ему управление Airfoil: macOS покажет запрос Automation (System Settings -> Privacy & Security -> Automation -> NodeApp -> Airfoil). Без этого AppleScript-мост не работает.
4. Замер output_latency_offset_ms (делается вдвоём на созвоне, после запуска всей системы):
   1. Выставить обоим нодам offset 0 (/offset a 0, /offset b 0).
   2. Выполнить /offset_test: обе ноды проигрывают 5 кликов, запланированных на одинаковые моменты времени.
   3. На созвоне слышно, чей клик раньше. Двигать offset отстающей стороны... точнее: offset задаёт, насколько РАНЬШЕ нода должна стартовать, поэтому увеличиваем offset той ноды, чей звук опаздывает. Шаг 100 мс, затем 25 мс.
   4. Повторять /offset_test до субъективной одновременности (щелчки сливаются или дают стабильное эхо < ~50 мс).
   5. Значения сохраняются командой /offset и переживают рестарты.
5. Перепроверять замер при замене или добавлении колонки, смене её прошивки, обновлении Airfoil.

Примечания: абсолютная величина offset может быть большой (AirPlay плюс буферизация Airfoil): это нормально, важна только скомпенсированная разница между домами. Синхронность нескольких колонок внутри одного дома обеспечивает сам Airfoil, калибровки offset она не требует.

## 15. Telegram-бот и аккаунты Spotify

1. Создать бота через BotFather: имя, токен. Токен в конфиг координатора.
2. Отключить у бота privacy mode (BotFather -> /setprivacy -> Disable), чтобы он видел обычные сообщения (ссылки) в группе.
3. Узнать свои user_id (любым способом, например бот userinfobot), вписать map в конфиг: id -> a, id -> b.
4. Создать группу: два пользователя + бот.
5. Spotify: два действующих Premium-аккаунта (по одному на дом). Проверить, что регионы аккаунтов дают пересекающийся каталог (пробные треки в приёмке).

## 16. VPS и деплой координатора

1. VPS: минимальный (1 vCPU, 1 ГБ RAM, 10 ГБ диска), Ubuntu 24.04 LTS. Публичные входящие порты: не нужны ни одного (SSH: через Tailscale SSH; Telegram: long polling наружу; ноды: внутрь по tailnet).
2. Установить: tailscale (глава 11), ffmpeg (`apt install ffmpeg`).
3. Каталоги: /etc/duet/ (конфиг, chmod 600), /var/lib/duet/ (SQLite, media).
4. Доставить бинарь координатора, установить systemd unit (приложение B), `systemctl enable --now duet-coordinator`.
5. Бэкап: ежедневный cron: `sqlite3 /var/lib/duet/duet.db ".backup /var/lib/duet/backup/duet-$(date +%u).db"` (недельная ротация). Media-каталог не бэкапится (эфемерные данные).
6. Firewall ОС (ufw): default deny incoming; allow in on tailscale0.

Проверка: `curl http://coord:8080/healthz` с любого мака отвечает 200; бот отвечает на /status.

# Часть IV. Качество и план

## 17. Нефункциональные требования

| Область | Требование |
|---|---|
| Синхронизация | Рассинхрон стартов между домами после калибровки: цель <= 150 мс, допустимо <= 500 мс. Фактическое значение каждого старта пишется в журнал (по started обеих нод) |
| Задержка вставки | От отправки голосового до готовности к эфиру: <= 15 с (скачивание + ffmpeg). Проигрывание: после текущего трека |
| Пауза между треками (shared) | <= 2.5 с при онлайне обеих нод и RTT tailnet < 150 мс |
| Восстановление | Смерть go-librespot: звук возвращается <= 15 с. Ребут мака: нода online <= 2 мин после загрузки ОС. Рестарт координатора: сессия в PAUSED, данные не теряются |
| Ресурсы | NodeApp: < 5% CPU Apple Silicon в steady state, RAM < 200 МБ. Координатор: < 100 МБ RAM без обработки медиа |
| Логи | Ротация на всех компонентах, суммарно < 500 МБ на машину; уровень по умолчанию info |
| Безопасность | Секреты только в конфигах chmod 600, не в репозитории. WS и media: токены нод. Bind всех слушателей только на tailnet-адреса. Публичных портов нет |
| Часы | Системный NTP включён на всех машинах; поправка протоколом (8.5) точностью +-20 мс |
| Приватность | Голосовые: только на VPS заказчика, ретеншн 30 дней, доступ только у двух нод по токенам |

## 18. Приёмочные критерии

Все проверки: на реальных двух домах (или имитации: два мака в разных сетях через tailnet), результаты фиксируются в чеклисте.

1. Ссылка на трек в чат -> трек играет в обоих домах; рассинхрон по журналу <= 150 мс; на созвоне клик-тест (/offset_test) звучит одновременно.
2. Голосовое (<= 3 мин) в чат во время трека -> играет в обоих домах после окончания текущего трека, до следующего трека; громкость субъективно на уровне музыки (и |I - (-14)| <= 2 LU по отчёту loudnorm).
3. Голосовое с подписью "лично" -> у партнёра играет, у отправителя тишина той же длительности; следующий трек стартует синхронно.
4. /playnow, /skip, /pause, /resume, /queue, /cancel, /vol работают согласно главе 9.
5. kill -9 процесса go-librespot на одной ноде во время shared -> звук в этом доме возвращается <= 15 с, элемент перезапущен на обеих нодах либо продолжен, в чате уведомление.
6. Обрыв сети ноды на 30 с в shared -> обе ноды в паузе <= 15 с от обрыва, сообщение в чат; после восстановления /resume продолжает тот же элемент, позиция +-2 с.
7. Ребут мака B -> нода сама поднимается, регистрируется; /status показывает online; воспроизведение возобновляется командой.
8. /mode solo -> каждый управляет своей нодой из своего Spotify; /inject ставит трек партнёру (или задокументированный fallback); голосовое в solo играет у партнёра на ближайшей границе трека.
9. Трек, недоступный на одном аккаунте -> пропуск с сообщением в чат, сессия продолжается.
10. Рестарт координатора во время PLAYING -> после старта сессия в PAUSED, очередь цела, /resume работает.
11. Сообщения от постороннего user_id ботом игнорируются.
12. На VPS нет открытых публичных портов (проверка nmap снаружи).
13. Airfoil: при двух колонках в одном доме обе играют без слышимого рассинхрона между собой; выключение одной колонки из розетки -> degraded и уведомление в чат, после включения колонка переподключается автоматически (<= 60 с), эфир при этом не прерывается на оставшейся.

## 19. Фазы и скоуп

Фаза 0. Spike (обязательна до основной разработки, результат: отчёт + прототип):
- Прототип на одном маке: go-librespot (pipe, f32le) -> FIFO -> минимальный AVAudioEngine-проигрыватель. Подтвердить: формат, поведение пайпа при паузе/смене трека, стабильность.
- Чеклист возможностей API go-librespot (по его документации и живой проверке): load в паузе с позицией; события границы трека и их задержка; чтение позиции; add to queue; поведение при недоступном треке. Каждый пункт: есть / нет / обходится так-то.
- Захват Airfoil'ом NodeApp, собранного как .app bundle: источник выбирается AppleScript'ом по POSIX-пути, звук идёт на колонку.
- AppleScript-мост из Swift-процесса: connect/disconnect/volume/connected работают надёжно (включая Automation-разрешение).
- Замер порядка величины сквозной задержки тракта (librespot -> движок -> Airfoil -> колонка).
- По результатам: зафиксировать решения по solo_inject (8.3) и, при необходимости, скорректировать механику load/resume (6.3).

Фаза 1. MVP:
- NodeApp полностью (исполнитель solo_inject допустимо отложить в фазу 2 вместе с командой /inject).
- Координатор: shared-режим, очередь (треки по ссылкам + голосовые оба таргета), state-машина, планировщик, часы.
- Telegram: команды главы 9, кроме /inject.
- Медиа-пайплайн (пресет default).
- Ручной сетап обоих домов и VPS по части III, калибровка offset.
- Приёмка: пункты 1-7, 9-12.

Фаза 2:
- Solo-режим целиком: /inject, голосовые в solo (приёмка п.8).
- Раскрытие ссылок на плейлисты/альбомы в треки.
- Пресет radio для вставок; режим наложения на хвост трека (ducking: -12 дБ, атака 250 мс, релиз 600 мс) как альтернатива вставке между треками.
- Поиск треков текстом (потребует Spotify Web API и регистрации приложения: отдельное решение).
- Команда /speakers [a|b] [имена]: управление набором активных колонок дома через Airfoil из чата.
- Airfoil Satellite как дополнительный приёмник (бесплатный, iOS/Mac/Windows/Android): телефон с наушниками как ещё одна "колонка" дома, например для ночного прослушивания. Satellite появляется в списке выходов Airfoil, механика не меняется.

Вне скоупа (не делаем без нового ТЗ): TTS; больше двух домов/пользователей; gapless и кроссфейды; мобильное приложение; какой-либо публичный доступ.

## C. Глоссарий

| Термин | Значение |
|---|---|
| Нода | Мак в доме: go-librespot + NodeApp + Airfoil + колонки |
| Airfoil | Приложение Rogue Amoeba: захватывает звук NodeApp и раздаёт на 1..N колонок дома в синхроне; управляется AppleScript |
| Координатор | Сервис на VPS: сессия, очередь, бот, медиа |
| Элемент | Единица эфира: track или voice (5.1) |
| Эфир | То, что звучит в рамках shared-сессии в обоих домах |
| Вставка (дроп) | Обработанное голосовое сообщение как элемент эфира |
| shared / solo | Режимы: общий синхронный поток / независимое прослушивание с inject |
| offset | output_latency_offset_ms: калибровочная задержка тракта ноды |
| tailnet | Приватная сеть Tailscale из трёх машин |
| Spike | Фаза 0: проверка гипотез об API go-librespot и аудиотракте до основной разработки |
